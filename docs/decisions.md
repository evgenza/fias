# Ключевые решения рефакторинга

Краткая фиксация решений по требованиям задания (см. docs/refactoring-log.md
для полных отчётов по этапам).

## Границы моделей и ORM (этапы 3–4)

- Источник полей, XML/JSON-тегов и SQL-типов — `ent/schema`. Из него
  `cmd/gar-gen-records` генерирует независимые записи `internal/gar/record`
  (зависимость от Ent только на этапе генерации; готовые records импортируют
  лишь gartype/gar/garxml).
- Ent-модели остаются представлением хранения; сгенерированные адаптеры
  (`ent/template/gar_batch.tmpl`) строят builders из records и реализуют
  `record.Handler`. Тест соответствия `TestRecordsMatchEntModels` не даёт
  записям и моделям разъехаться.
- Направления зависимостей: `gar/record` не импортирует Ent/ZIP/CLI;
  `importjob` не импортирует ent/sql/zip/xml (порты `Archive` и `Writer`
  объявлены со стороны сценария); `storage` реализует порты; composition root —
  `internal/cli` + `cmd/gar-importer`.
- Спецификации обязательности/ограничений атрибутов генерируются из
  закреплённых XSD (каталог `xsd/`) командой `cmd/gar-gen-spec`; соответствие
  Ent-схемам проверяется тестами (единственное ожидаемое отличие —
  синтетический `param.source`).

## Идентичность и покрытие выпусков (этапы 2, 6–7 — частично)

- Регион определяется единообразно (`gar.RegionCode`): папка 1..99,
  обёртки `gar_xml/` и `gar_delta_xml/` поддержаны явно; неожиданный путь —
  ошибка плана, а не «общероссийский файл».
- Дата имени файла — календарный день (gartype.Date); `sequence` файла —
  идентификатор, а не порядок выпуска (иных подтверждений нет).
- Голый `AS_PARAM` без семейства объектов — unknown; не создаёт неоднозначный
  источник в БД. Точный фильтр `--formats AS_HOUSES_PARAMS` выбирает только
  своё семейство.
- Дельта-правила (VersionId, предшественник, удаления) НЕ реализованы:
  перед реализацией этапа 8 требуется подтверждение по реальным fixture-выпускам.

## Транзакции и checkpoint (этапы 4–6 — частично)

- Пакет записывается upsert-ом (`CreateBulk` + `OnConflictColumns`) в одной
  транзакции Ent; счётчики подтверждённых записей и операций записи
  увеличиваются только после успешного коммита.
- Checkpoint по позиции входа, digest архива, возобновление и `gar_control`
  (datasets/import_runs/import_files/publications) — этап 6 (не реализовано).

## Миграционный baseline (этап 5)

- Раннер `internal/migrations`: формат каталога Atlas (`*.up.sql`, `atlas.sum`,
  генерация — `cmd/gar-migrate-diff` по одноразовой dev-базе через Ent/Atlas
  diff), реестр ревизий `gar_control.atlas_schema_revisions` в формате Atlas,
  advisory-lock на закреплённом соединении, sha256 применённых версий.
- `Schema.Create` (automatic migrations) как механизм для рабочей БД удалён —
  один механизм применения (versioned apply). `--write-sql` удалён: планы
  генерирует `cmd/gar-migrate-diff`, целевая база не участвует.
- `migrate --baseline` помечает legacy-схему применённой только после проверки
  фактического состояния (таблицы/столбцы по метаданным Ent); при отличиях —
  отказ с указанием отличий. Процедура восстановления legacy `param`:
  `migrations/legacy/README.md` (nullable → проверяемый backfill → NOT NULL →
  частичный уникальный индекс; неизвестное происхождение не выдумывается).
- Atlas CLI как Go-инструмент не закреплён: `ariga.io/atlas/cmd/atlas`
  (v0.13.1) несовместим с текущим tablewriter, сборка master падает на
  pg_query_go v5.1.0 на macOS (strchrnul vs XCode SDK). Формат каталога и
  реестра ревизий Atlas-совместим — при появлении рабочего бинарника CLI
  подключается без изменения схемы данных.

## Публикация (этап 7) — не реализовано

План: отдельная схема `gar_data_<id>` на snapshots, указатель
`publications.active_dataset_id` в `gar_control`, закрепление dataset за
читателем. До реализации — `gar` остаётся единственной схемой данных.
